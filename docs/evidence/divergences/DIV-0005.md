  behavior, and value-model migration interface/lifetime work.

- Observed OxVBA result:
  - Historical OxVBA builds treated `Class_Initialize`/`Class_Terminate` as
    normative hooks but did not reliably trigger `Class_Terminate` on ordinary
    internal class lifetime teardown. The March 2026 oracle capture recorded
    `class_lifecycle_terminate_fail.bas` as Excel `ok: 1` while the then-current
    golden result was an error.
  - Current VM3 internal project objects are `ObjectRef`-backed, refcounted
    project instances. Last release parks the original instance, VM3 drains
    `Class_Terminate` at statement/procedure boundaries to a fixpoint, suppresses
    termination faults, honors resurrection, and releases object fields after
    termination.
  - The current oracle/golden reconciliation records
    `class_lifecycle_terminate_fail.bas` as `ok i16:1` for both Excel and OxVBA.
  - Focused VM3 differential coverage now pins:
    - `Set x = Nothing` statement-boundary termination,
    - caught fault unwinding from a callee with local object teardown,
    - failed `Class_Initialize` cleanup and child-field cascade drain,
    - source-level `Class_Terminate` `Me` resurrection without field loss or
      double termination on the later drop,
    - predeclared singleton initializer failure cleanup and retry semantics.
- Office VBA expected behavior:
  - `Class_Terminate` is part of the observable object-lifetime contract and
    runs on deterministic teardown/final-release paths.
- Tracking status:
  - Closed for the originally recorded internal VM/class-lifetime mismatch.
  - Historical profile CSVs under `docs/evidence/profiles/` still record older
    failures and should be read as immutable historical artifacts, not current
    status.
  - Outward COM server/export object release behavior is separate `IP-06` scope;
    this record does not claim live Windows COM export parity.
