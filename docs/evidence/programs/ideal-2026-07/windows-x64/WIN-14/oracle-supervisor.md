## Scope and credit

This evidence covers the authority, containment, protocol, fixture, and attachment repair checks for the Excel/VBA oracle supervisor. It failed before VBE access or workbook mutation and therefore claims no live case success, Excel/VBA behavioral result, canonical matrix row, release, certification, or capability credit.

The later live run must still use the characterized Windows x64 / 64-bit Excel development-oracle environment with `-NoMatrixUpdate`, capture the selected default five cases, and run the bounded `runtime-unhandled-modal` diagnostic when that transcript is needed. Release certification remains assigned to the clean pinned certification VM.

## Authority boundaries implemented

- Fallback process cleanup opens one `SafeProcessHandle` and uses that same retained handle for executable/start-time identity, termination, and wait. A PID is never reopened between validation and action. Missing, reused, and same-instance-conflict identities fail closed; only the exact retained process can be terminated.
- Each live run uses a GUID-based default run ID and an atomic `FileMode.CreateNew`, `FileShare.None` claim held through the run. A top-level `finally` releases only that exact claim on every post-claim success or failure path while preserving failed evidence. Both failed entry and normal exit use the same hardened cleanup: claim-stream disposal and marker deletion failures are accumulated, the exact marker must be absent afterward, and cleanup failure is surfaced without erasing primary failure context. Reused run directories and concurrent equal run IDs are rejected; different IDs remain isolated. The run directory is not created through `-Force`.
- The supervisor assigns the waiting worker to a kill-on-close Job and positively queries membership before publishing containment authority. The worker validates the exact Boolean membership assertion before any case mutation. Post-cleanup authority binds the result to the supervisor-retained worker PID, process start UTC, and executable path, and requires worker start <= containment publication <= result generation. Every retained Excel and helper ownership record independently preserves process start <= ownership acquisition, with both timestamps at or after containment publication and at or before result generation; plausible exact identities outside that interval fail closed.
- VBE command ID 578 execution is enclosed by exact active project, active module, active code-pane, and injected-source-hash snapshots immediately before and after `Execute()`.
- Active project/module/code-pane values inspected by those snapshots are borrowed RCW aliases. The helper never final-releases them; explicit COM release remains at the case-owner boundary so authority inspection cannot invalidate the live project between snapshots or before runtime measurement.
- Compile-error acceptance uses only the immutable guardian observation written before dismissal. The expected token and exact injected source line are case-bound. Post-dismiss COM selection is retained as diagnostic data only and cannot repair the observation.
- Guardian controls use a strict v2 schema with exact run/case/operation identity, positive sequence, phase, JSON Boolean dismissal authority, and timestamp. Invalid controls are durably reported and never arm an operation or authorize dismissal. Compile, run, and cleanup use separate dialog-classification allowlists.
- Every operation requires a guardian arm acknowledgement and a strictly sequenced heartbeat after the invocation completes. Evidence flush fails if the heartbeat does not span the invocation, including the ready/benign-then-hang shape. Every guardian event carries the exact watched Excel PID. On controlled shutdown, the guardian itself appends the causally latest and final-sequence state containing that Excel PID, its exact guardian PID/start/name/path, stop-file observation, still-live Excel identity, and exit reason; any non-controlled exit is nonzero.
- Job tests cover explicit termination, dispose-only handle closure, abrupt supervisor death, and children created before their ownership ledger entry. In every case the kill-on-close Job removes the contained worker/child.
- Runtime adjudication records measured VBOM access, invoked-entry existence, nested macro target existence, and configured AutomationSecurity separately. The worker passes sealed nullable procedure/target values without string casts or typed-parameter coercion into the shared production measurement constructor, so compile-failure and intrinsic-shadow retain JSON null rather than an invented empty string. Runnable entry is true only after an observed qualified return, case-specific return sentinel, or owned unhandled-runtime modal; configuration is never used as a substitute. The default caught full-`Err` case remains. A separate live diagnostic case raises an unhandled VBA error so an owned runtime-error modal transcript can be captured without weakening the default self-test.
- Ownership, guardian, result, and plan evidence is bound to the selected case set. Case identities are unique. After worker quiescence, the supervisor opens each supervisor-derived per-case `guardian-events.jsonl` path once, retains its exact bytes and SHA-256, and passes that sealed evidence to the pure resolver. Modal, heartbeat, and final-health authority derives only from those supervisor-retained bytes. Worker-embedded record copies and liveness Booleans must match afterward and cannot grant authority. Every retained guardian event PID and the final state must equal the exact per-case Excel ownership-ledger PID; the final state also binds to the exact helper ownership identity and must be the last sequence record with no earlier event timestamp after it. Ledger validation checks JSON scalar types, timestamps, phases, sequence monotonicity, capture-before-dismiss ordering, requested buttons, the actual dismissed button, and exact case order/count where one record per case is required.
- Excel attachment enumerates top-level windows for the exact directly launched PID and their exact-PID descendants. Enumeration has a separate 512-window authority bound: native truncation, API failure, foreign PID, or malformed enumeration fails before attachment. The diagnostic retains at most 128 last-window descriptions and 256 HRESULT observations without limiting the complete admitted candidate set. `OBJID_NATIVEOM` is accepted only from `EXCEL7`, and returned `Application.Hwnd` must resolve back to the launch PID. PID/start/path, exact launch argv, bootstrap identity, HWND/class/title/visibility, HRESULT, enumeration outcome, and result are recorded. Visible owned startup/modal surfaces fail closed without broad dismissal.
- Each case creates a byte-deterministic, macro-free, five-part OpenXML `.xlsx` bootstrap package. The bootstrap validator pins the part order/set, XML and content types, root/workbook relationship identities and target closure, macro absence, and recorded hash. The result's module path, bootstrap path, and compile-context project file must first equal the supervisor-derived output-directory/case paths; an unrelated valid workbook is not opened or admitted. `ProcessStartInfo.ArgumentList` must contain exactly `/x` and the bootstrap path—no string-concatenated command and no `/n`. The attached process must open exactly that workbook, `Workbooks.Add` is not used, and missing or modified bootstrap bytes fail before launch or after close-without-save.
- The supervisor seals and serializes the selected case sequence before worker launch. Each immutable descriptor binds case order/ID/purpose, module name and normalized source hash, expected compile/run statuses, nullable run procedure, diagnostic mode, evidence contract, expected value/token/line, and full expected `Err` state. The aggregate sequence digest travels separately on the worker command line. The worker validates that digest before waiting for containment, consumes only the transmitted descriptor objects, and never rebuilds a parallel case catalog. The result echoes the aggregate and per-case digests.
- The pure post-cleanup validator derives compile status from exact command ID/enabled state, active project/module/code-pane/source snapshots, guardian modal evidence, and execution result. Any non-null `Execute()` exception derives `harness-error` before modal classification; a coincident compile-error modal cannot downgrade it. Guardian liveness before cleanup is a separate required success fact from independently recomputed compile/run operation health.
- Runtime invocation and status derive without consulting `run_status`: the sealed descriptor, derived compile outcome, supervisor-retained guardian run ledger, exact entry/target/configuration measurements, and exact outcome-specific observation must form one mutually exclusive shape. Return success excludes modal and `Err`; full-`Err` success binds the exact six-field returned JSON case-sensitively to the separately persisted typed `runtime_err`, which in turn binds case-sensitively to the sealed descriptor; ambiguous macro failure binds the sentinel suffix to a freshly derived missing-macro disposition and excludes `Err`; the diagnostic runtime-modal shape excludes value and `Err`. Successful outcomes require null `transport_error`; every behavioral, evidence-only, or authority failure requires a specific nonempty transport. Every authoritative case/guardian timestamp is at or after containment publication and at or before `results.generated_utc`. Only after derivation are worker `compile_status`, `run_status`, macro-disposition, per-case `passed`, and aggregate `passed` labels compared. Complete cases require `observed_excel_pid == owned_excel_pid == ledger.pid`; versioned nullable compile-command/execution/context, runtime-measurement/`Err`, and evidence-status objects are schema/type checked. Process exit alone never bypasses ledger binding. The only partial-result disposition is exactly the first selected case failing with `harness-error`, no durable owned PID, no compile/run/runtime/guardian evidence, nonempty transport, both ownership ledgers exactly empty, and exit code 1 after successful Job cleanup. Its sealed `preownership_failure_phase` advances monotonically from `bootstrap-construction` to `excel-attachment` to `excel-ownership`, then clears only after the ownership record is durable. Null bootstrap is admitted only for the construction phase. Attachment/ownership failures require the exact supervisor-derived, hash-stable bootstrap, and the supervisor validates those retained workbook bytes before surfacing transport.
- Exact Excel launch arguments and attachment decisions are separately testable pure functions. `ProcessStartInfo` construction produces exactly `['/x', bootstrap-path]`. Attachment adjudication rejects incomplete/foreign enumeration, visible owned blockers, non-`EXCEL7` candidates, failed/null native object retrieval, and returned `Application.Hwnd` PID mismatch. Worker Job creation and process start share one cleanup scope; injected start, assignment, and membership failures prove deterministic termination of real waiting children and Job disposal before authority publication.
