## 4. Syntax layer today: lexer + green/red tree scaffolding

The syntax system is real but intentionally minimal.

### 4.1 Token kinds currently modeled

From `crates/oxvba-syntax/src/syntax_kind.rs`:

```rust
pub enum SyntaxKind {
    Identifier,
    Number,
    StringLiteral,
    Keyword,
    Symbol,
    Trivia,
    EndOfFile,
}
```

### 4.2 Green tree shape today

From `crates/oxvba-syntax/src/green.rs`:

```rust
pub struct GreenNode {
    pub width: usize,
    pub children: Vec<String>,
}
```

So green nodes currently store token text fragments (`children`) and aggregate width.

### 4.3 Red tree shape today

From `crates/oxvba-syntax/src/red.rs`:

```rust
pub struct RedNode<'a> {
    pub green: &'a GreenNode,
    pub absolute_offset: usize,
}
```

So red nodes currently wrap green with absolute offset (currently initialized to `0`).

## 5. Compiler pipeline today (implemented path)

Current high-level compile entry (`crates/oxvba-compiler/src/lib.rs`):

```rust
let bound = resolve::resolve_symbols(source);
let checked = typecheck::check_types(bound).map_err(CompileError::TypeError)?;
let _hir = lower_to_hir::lower_to_hir(&checked);
Ok(emit::emit_bytecode(&checked))
```

### 5.1 Resolver supports a narrow statement set

`BoundOp` currently:

```rust
pub enum BoundOp {
    AssignConst { name: String, value: i32 },
    AddConst { name: String, value: i32 },
    SubConst { name: String, value: i32 },
    Unsupported { line: String },
}
```

### 5.2 Typechecker behavior

- Enforces `Option Explicit` undeclared-variable error.
- Rejects unsupported statements immediately.

```rust
BoundOp::Unsupported { line } => {
    return Err(format!("unsupported statement: {line}"));
}
```

### 5.3 Bytecode “IL” exists and is executable

Bytecode instruction enum (`crates/oxvba-compiler/src/bytecode.rs`):

```rust
pub enum Instruction {
    LoadConstI32 { slot: usize, value: i32 },
    AddConstI32 { slot: usize, value: i32 },
    SubConstI32 { slot: usize, value: i32 },
    Halt,
}
```

Probe output for `x=20; x=x-4`:

```text
BYTECODE_SLOT_COUNT:1
BC[00] LoadConstI32 { slot: 0, value: 20 }
BC[01] SubConstI32 { slot: 0, value: 4 }
BC[02] Halt
```

So if you mean “IL” as executable intermediate language, yes: a small register-slot bytecode IL is in place.

## 6. Interpreter/VM today

VM execution loop supports the current instruction set and mutates slot registers:

```rust
match instr {
    Instruction::LoadConstI32 { slot, value } => { ... }
    Instruction::AddConstI32 { slot, value } => { ... }
    Instruction::SubConstI32 { slot, value } => { ... }
    Instruction::Halt => break,
}
```

Probe output:

```text
VM_SNAPSHOT:[16]
```

Meaning: compile -> bytecode -> VM execution is live.

## 7. Is JIT actually in place?

Short answer: toggle path exists; real JIT backend is still scaffold.

`crates/oxvba-jit/src/lib.rs`:

```rust
pub fn compile_function(&self, _symbol: &str) -> Result<(), JitError> {
    Err(JitError::NotEnabled)
}
```

Host engine does this when `enable_jit=true`:

```rust
if self.config.enable_jit {
    let _ = self.jit.compile_function("main");
}
execute_and_snapshot(&bytecode)
```

Because that result is ignored, execution still succeeds through VM path.

Probe output confirms parity at this stage:

```text
ENGINE_VM:Ok([16])
ENGINE_JIT_TOGGLE:Ok([16])
```

So: the “JIT switch” interface is present, but computation is still VM-executed.

## 8. IR status (HIR/MIR/CFG)

The dedicated IR crate exists (`oxvba-ir`) but is currently scaffold-level containers + pass-through lowering.

Types:

```rust
pub struct VbaHir { pub procedures: Vec<String> }
pub struct VbaMir { pub blocks: Vec<String> }
pub struct CfgIr  { pub nodes: Vec<String> }
```

Lowering currently clones sequence (`procedures -> blocks -> nodes`) rather than modeling semantics.

This is important context: there is architectural groundwork, but not full semantic IR lowering yet.

## 9. What the current MVP profile really means

Declared profile scope (`mvp-int32-core-v1`) is intentionally narrow and stabilized for:

- Windows x64 local runs.
- VM backend behavior.
- JIT toggle parity behavior (currently same effective execution path).
- Conformance corpus focused on integer slot arithmetic + `Option Explicit` checks.

Matrix artifacts:
- `docs/evidence/phase12/matrix_latest.csv`
