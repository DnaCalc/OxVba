# Code Review — 2026-03-09

10 suggestions for real improvement across the OxVba codebase.

---

## 1. Split `standard.rs` (7,385 lines) into modules

This file contains the HAL adapter, the entire controlled COM test fixture (~1,200 lines of vtable/dispatch logic), event sink implementations, typelib metadata builders, GUID helpers, raw COM FFI, and 80+ tests. Extract at minimum:
- `adapters/com_ffi.rs` — raw COM vtable structs, GUID constants, `unsafe` FFI helpers
- `adapters/test_dispatch.rs` — the `OxvbaTestDispatchObject` and all its vtable functions
- `adapters/com_event_sink.rs` — `OxvbaComEventSink`, `OxvbaComEventSourceInterfaceSink`, and their vtable impls
- `adapters/typelib_metadata.rs` — `build_typelib_metadata`, `known_typelib_identity_for_prog_id_name`, metadata constants

This file has 163 `unsafe` blocks. Isolating the raw COM FFI would make safety auditing tractable.

## 2. Remove redundant `arg0` field from `ComEventCallbackDispatch`

`engine.rs:95-96`: The struct carries both `arg0: i32` and `args: Vec<i32>`, where `arg0` is always `args[0]` (or 0 if empty). This was an artifact from when only single-arg callbacks existed. Every consumer can just use `args[0]`. Removing it eliminates a subtle correctness risk if `arg0` and `args[0]` ever diverge.

## 3. Deduplicate the `DISPATCH_INVOKE_MISSING_ARG_TOKEN` constant

Defined identically in both `crates/oxvba-hal/src/adapters/standard.rs:63` and `crates/oxvba-compiler/src/emit.rs:16`. Define it once in `oxvba-runtime` (which both crates already depend on) alongside the other value tag constants.

## 4. Fix hardcoded `HalProfileId::Windows` defaults

Both `oxvba-vm/src/interpreter.rs:44` and `oxvba-jit/src/lib.rs:47` define `fn default_host_services()` that hardcodes `HalProfileId::Windows`. On Linux/Mac these defaults silently use the wrong profile. Use `cfg`-based selection or a shared `default_profile()` function.

## 5. Widen `ComHal::dispatch_invoke` beyond single-argument calls

The current signature `dispatch_invoke(object, member, arg) -> i32` only supports one argument. The pair-event trigger (`FirePairChanged`) works around this by taking one arg and synthesizing the second internally. A proper fix would be `dispatch_invoke(object, member, args: &[i32])` or a separate `dispatch_invoke_multi` method so callers can pass the real argument vector.

## 6. Move environment variable reads to initialization time

Functions like `force_registered_test_dispatch()`, `com_event_trace_enabled()` (which check `std::env::var` on every call), and the optimizer toggle `OXVBA_DISABLE_OPT` in `compiler/src/lib.rs:56` re-read env vars at every invocation site. Cache these in the adapter/config structs at construction time. This is both a performance issue and a correctness issue (env vars could change mid-execution, causing inconsistent behavior).

## 7. Add `#[must_use]` to `HalResult<T>` return types on trait methods

`ComHal`, `FileSystemHal`, `EventPumpHal`, etc. all return `HalResult<T>` but none of the trait methods are marked `#[must_use]`. A caller could silently ignore a failed `unsubscribe_event` or `close` and leak resources. Adding `#[must_use]` to the traits or the methods catches these at compile time.

## 8. Replace raw pointer casting with typed wrappers for COM object handles

The COM layer uses `i32` tokens for object handles, subscription tokens, and callback tokens — all the same type. It's trivial to mix them up (pass a subscription token where an object token is expected). Newtype wrappers (`struct ComObjectHandle(i32)`, `struct ComSubscriptionToken(i32)`, `struct ComCallbackToken(i32)`) would make the API self-documenting and catch misuse at compile time without any runtime cost.

## 9. Consolidate the `Vm::execute` reset sequence

`interpreter.rs:130-182`: Three entry points (`execute`, `execute_with_typed_fastpaths`, `invoke_procedure_with_i32_args`) each manually reset `call_stack`, `on_error_resume_next`, `on_error_goto_label_target`, etc. in slightly different ways (`execute` clears `withevents_bindings` but `invoke_procedure` doesn't). Extract a `reset_execution_state(preserve_bindings: bool)` method to guarantee consistent initialization and prevent future divergence.

## 10. Add integration test coverage for cross-platform HAL profiles

The test suite is heavily Windows-focused (COM tests are `#[cfg(target_os = "windows")]`). The Linux/Mac/Wasm/Null adapter paths in `standard.rs` are mostly stub returns with no tests exercising them end-to-end. A `#[test]` that runs `Engine::execute_source_with_snapshot` against each profile for a basic VBA program (no COM) would catch regressions in the non-Windows paths that are currently invisible.

# HAL Interface Review — COM Interop Focus

Focused review of the `HostServices` / `ComHal` / `EventPumpHal` / `TypeLibraryHal` trait surface and the relationship between the trait contracts, the adapter implementation in `standard.rs`, and the `oxvba-com` crate.

---

## H1. `EventPumpHal::do_events` is a covert COM callback delivery channel

`do_events()` has two unrelated responsibilities smuggled into one method:

1. **Pump host messages** (Windows message loop, thread yield) — a general runtime concern.
2. **Dequeue and return a COM callback token** from `ComState.pending_callbacks` — a COM-specific concern.

The method signature `fn do_events(&self) -> HalResult<ValueToken>` returns `0` for "no callback" or a callback token. The host engine (`engine.rs:311-377`) then makes 4 additional `ComHal` calls (`event_callback_subscription`, `event_callback_arity`, `event_callback_arg` x N, `release_event_callback`) to reconstruct the callback payload.

**Problems:**
- The host engine has to know the callback-interrogation protocol. It isn't encoded in the trait — it's a fragile multi-step convention spread across `engine.rs` and `standard.rs`.
- `EventPumpHal` and `ComHal` are supposed to be separate capabilities, but `do_events()` secretly reaches into `ComState`. The NullHostServices dutifully returns an error for `do_events()`, but a profile that supports events but not COM would be impossible to implement cleanly.
- On non-Windows profiles, `do_events` never returns a callback token (always `0`), so the return value is semantically different per platform — it's not truly a "pump events" abstraction.

**Recommendation:** Split into two methods: `EventPumpHal::pump()` (message loop, no return value) and `ComHal::poll_callback() -> Option<ComCallbackPayload>` that returns a complete payload struct. This eliminates the multi-call interrogation protocol and the capability cross-contamination.

## H2. `ComHal::dispatch_invoke` does double duty as an event trigger

`dispatch_invoke` both invokes a COM member *and* queues event callbacks as a side effect via `queue_com_event_callbacks()`. When the caller invokes `FireChanged(21)`, the method returns the member's return value AND silently enqueues a callback into `ComState.pending_callbacks`, which the caller later discovers through the `EventPumpHal::do_events()` channel.

This side-effect coupling means:
- The trait contract says nothing about event triggering. A new `ComHal` implementor would have no way to know that `dispatch_invoke` is supposed to queue callbacks.
- The projection path (synthetic callback queueing from member-token to event-token mapping) is hardcoded knowledge in the adapter, not in the trait.
- Native connection-point callbacks bypass this entirely — they arrive via the sink's `IDispatch::Invoke` and enqueue directly into `ComState`. So the same logical operation (trigger -> callback) takes two completely different code paths depending on transport.

**Recommendation:** Make event triggering explicit. Either add `ComHal::trigger_event(object, event, args)` as a trait method, or document that `dispatch_invoke` has trigger semantics only when the member matches a `Fire*`/`Raise*` convention — and move the projection queueing logic into the trait default implementation so it's visible to implementors.

## H3. The callback interrogation API is a chatty RPC protocol disguised as a trait

The current `ComHal` requires 5 calls to consume one callback:

```
do_events()                         -> callback_token
event_callback_subscription(token)  -> subscription
event_callback_arity(token)         -> arity
event_callback_arg(token, 0..N)     -> arg values
release_event_callback(token)       -> cleanup
```

This is 3 + N calls for an N-argument callback. Each call acquires the `ComState` mutex, validates capability/policy guards, and looks up the callback in a `BTreeMap`. The `engine.rs` `poll_com_event_callback` method (lines 311-377) is entirely boilerplate for this protocol.

**Recommendation:** Replace with a single `ComHal::poll_callback(&self) -> HalResult<Option<ComCallbackPayload>>` where `ComCallbackPayload` is:
```rust
pub struct ComCallbackPayload {
    pub subscription: ValueToken,
    pub event: ValueToken,
    pub args: Vec<ValueToken>,
}
```
This eliminates 5 trait methods, ~150 lines of boilerplate in `standard.rs`, and 60 lines of orchestration in `engine.rs`. The individual methods (`event_callback_subscription`, `event_callback_arity`, `event_callback_arg`, `release_event_callback`) exist only to serve this one call sequence — they have no independent utility.

## H4. `ComHal` conflates object lifecycle, dispatch, and event management

The current `ComHal` trait handles:
- Object activation (`create_object`)
- Member dispatch (`dispatch_invoke`)
- Event subscription lifecycle (`subscribe_event`, `unsubscribe_event`)
- Callback delivery/interrogation (5 methods)

These are three distinct concerns with different lifetimes and error modes. A `create_object` failure is an activation error. A `dispatch_invoke` failure is a runtime dispatch error. A `subscribe_event` failure is a connection-point handshake error. Lumping them under one trait means every implementor must handle all of them, and capability checks are repeated identically across 8 methods (the `supports(capability)` / `policy.allow_com_activation` / `native_com_enabled()` guard triple appears in every single method body).

**Recommendation:** Split into:
- `ComActivationHal` — `create_object`, `release_object` (currently missing)
- `ComDispatchHal` — `dispatch_invoke` (and future multi-arg variant)
- `ComEventHal` — `subscribe_event`, `unsubscribe_event`, `poll_callback`

This also makes it possible for a profile to support COM dispatch without COM events (e.g., a cross-platform IPC dispatch layer).

## H5. No `release_object` in `ComHal`

`create_object` allocates a handle in `ComState.bindings` and (on Windows) holds a raw `IDispatch` pointer. There is no corresponding `release_object` method. Object handles are never released. The `unsubscribe_event` method cleans up subscriptions and stale callbacks, but the binding itself — including the native `IDispatch` pointer — persists forever.

For short test runs this is harmless. For long-lived host sessions it is a COM reference leak.

**Recommendation:** Add `fn release_object(&self, object: ValueToken) -> HalResult<()>` that removes the binding from `ComState`, releases native resources, and tears down any remaining subscriptions.

## H6. `oxvba-com` crate is a skeleton that duplicates nothing and contributes nothing

The `oxvba-com` crate contains:
- `ComDispatch` trait with `fn invoke(&self, name: &str) -> DispatchResult` — never used anywhere
- `RefCount(u32)` — never used by the HAL (which uses `AtomicU32` directly)
- `CycleCollector` — empty stub
- `WindowsComBridge` / `PortableComBridge` — empty structs

No crate depends on `oxvba-com` for COM functionality. All real COM logic lives in `oxvba-hal::adapters::standard`. The `ComDispatch` trait in `oxvba-com` has a completely different design from `ComHal` in `oxvba-hal`.

**Recommendation:** Either delete `oxvba-com` or give it a real purpose — e.g., move the COM state machine (`ComState`, `ComBinding`, `ComEventSubscription`, `ComEventCallback`, etc.) out of `standard.rs` and into `oxvba-com`, making it the platform-independent COM state layer that the HAL adapters delegate to.

## H7. `TypeLibraryHal` is coupled to COM but lives in a separate trait with no bridge

`TypeLibraryHal` provides `resolve_typelib_reference` and `load_typelib_metadata`, which feed directly into `ComBinding` construction inside `create_object`. But the trait sits alongside `ComHal` as a peer under `HostServices`, and the metadata is consumed *inside* the `ComHal::create_object` implementation — not at the trait boundary.

The host engine and VM never call `TypeLibraryHal` directly. It's an internal dependency of the COM adapter, not a HAL contract that consumers interact with.

**Recommendation:** Make `TypeLibraryHal` an internal implementation detail of the COM adapter rather than a public HAL trait. The `HostServices` accessor `fn typelibs(&self) -> &dyn TypeLibraryHal` can be removed from the trait, simplifying the interface. If type library resolution ever needs to be exposed to consumers, it can be re-promoted with a cleaner contract.

## H8. Platform adapters are pure boilerplate wrappers

`WindowsHostServices`, `LinuxHostServices`, `MacOsHostServices` are each ~87 lines that wrap `StandardHostServices` and forward every trait method. They add no behavior. The `for_profile` factory already selects by `HalProfileId`:

```rust
match profile {
    HalProfileId::Windows => WindowsHostServices::boxed(...)
    HalProfileId::Linux => LinuxHostServices::boxed(...)
    ...
}
```

But `StandardHostServices` already stores `profile` and branches on it internally. The per-platform wrappers exist only to satisfy the type system — they add an extra indirection with no semantic value.

**Recommendation:** Have `StandardHostServices` implement `HostServices` directly (it already implements all the sub-traits). The per-platform wrapper files (`windows.rs`, `linux.rs`, `macos.rs`) can be deleted. The `for_profile` factory returns `Arc<StandardHostServices>`. Platform-specific behavior stays in `#[cfg]` blocks inside `StandardHostServices`, which is already how it works.

## H9. The controlled test dispatch object (`OxvbaTestDispatchObject`) is a 1,500+ line in-process COM server embedded in the HAL adapter

Lines ~3850-5100 of `standard.rs` are an entire COM server implementation: IUnknown, IDispatch, IConnectionPointContainer, IConnectionPoint, event sink vtables, static vtable constants, dispatch member routing, connection-point advise/unadvise, source-interface callback firing. This exists solely for testing.

It is not a HAL abstraction — it is a test fixture. Its presence in the adapter means:
- The adapter cannot be compiled without the test fixture.
- The vtable structs and `unsafe` blocks inflate the safety audit surface of the adapter.
- Adding new test members requires modifying the HAL adapter.

**Recommendation:** Move the entire controlled test dispatch object into a dedicated module (e.g., `adapters/controlled_test_server.rs` or better, into `oxvba-com/src/test_fixture.rs`). The adapter only needs a factory function: `fn create_controlled_test_dispatch() -> *mut RawIDispatch`. The vtable implementations, connection-point logic, and member routing all move out.

## H10. `ComState.pending_callbacks` is a `Vec<i32>` used as a queue — should be `VecDeque`

`standard.rs:3118`: `pending_callbacks: Vec<i32>` is consumed FIFO via `state.pending_callbacks.first()` + `state.pending_callbacks.remove(0)` (line 1760-1761). `Vec::remove(0)` is O(n) — it shifts all remaining elements. `VecDeque::pop_front()` is O(1). Under sustained callback load (e.g., Excel automation pumping events), this becomes quadratic.

## H11. The `ComHal` trait exposes no object identity or type information

After `create_object` returns a handle, there is no way to ask the HAL what kind of object it is. The host engine has no `get_prog_id(object)`, `get_object_type(object)`, or `supports_events(object)` method. All COM knowledge is trapped inside the adapter's `ComBinding` struct.

This means the host engine cannot make informed decisions about event capability, dispatch strategy, or error recovery without duplicating the adapter's internal knowledge. The `subscribe_com_event_handler` method in `engine.rs` just calls `subscribe_event` and hopes — it has no way to pre-check whether the object supports events.

**Recommendation:** Add `fn object_supports_events(&self, object: ValueToken) -> HalResult<bool>` and optionally `fn object_identity(&self, object: ValueToken) -> HalResult<String>` to give consumers visibility into object capabilities without exposing adapter internals.

**Assessment:** The *active* crate structure (compiler, vm, hal, host, runtime, jit, cli) is well-factored and each crate has a clear responsibility. The placeholder crates should either be populated or removed to avoid misleading new readers.

## Compiler Pipeline — 90%

The compiler is the strongest subsystem. Five passes with ~16,800 lines and 289 tests:

### Resolve Pass (5,285 lines, ~78 tests)
- Builds a complete bound AST (`BoundExpr`, `BoundStmt`, `BoundType`, `BoundCond`).
- 31 statement variants, 6 expression variants, 15 type variants, 5 condition variants.
- Handles: variable/procedure declarations, scoping, type inference, COM member resolution, project-aware symbol binding, `WithEvents`/`Implements`/`RaiseEvent` validation.
- **Quality:** Thorough and well-tested. The main concern is monolithic size — 5,285 lines in one file. Would benefit from splitting into symbol table, scope manager, and binder.

### Type Check Pass (1,880 lines, ~13 tests)
- Validates type consistency, detects name collisions, collects labels.
- **Quality:** Functional. Limited coercion rules (string coercion explicitly unimplemented in runtime).

### Optimize Pass (433 lines, ~10 tests + 1 Kani proof)
- Constant folding (`If 1=1 Then` → branch elimination).
- Dead code elimination (consecutive assignments, dead stores).
- Observable-effect tracking for safe dead store removal.
- **Quality:** Basic but correct. No SSA, no cross-block analysis, no loop optimizations. Adequate for the current execution model (VM-interpreted bytecodes where optimization returns are modest).

### Emit Pass (2,308 lines, ~6 tests + 1 Kani proof)
- Maps bound AST to 106 bytecode instruction variants.
- Manages slot allocation, call patches, label resolution.
- Generates runtime metadata (entry PC, param slots, external call descriptors).
- **Quality:** Mature and well-structured. Good separation between emission logic and bytecode format.

### Bytecode Format (514 lines, 106 instructions)
- Full instruction set covering: arithmetic, string operations, date/time, math/financial, array operations, type intrinsics, host service calls, COM/event intrinsics, WithEvents lifecycle, control flow, comparisons, logic.
- rkyv serialization for bytecode objects.
- **Quality:** Comprehensive instruction set. The 106-instruction count covers the full VBA 7.1 language surface targeted by v620.

### Project Compilation (4,718 lines, ~48 tests)
- Multi-module, multi-reference project compilation.
- Reference binding state machine (Unbound → Bound → Failed).
- Type library catalog entries and public symbol resolution (local-first, then references).
- Conditional compilation support.
- **Quality:** Well-designed with good test coverage.

**Overall compiler assessment:** The compiler pipeline is the most mature subsystem. Symbol resolution and emission are solid. The main gap is the non-functional IR layer — compilation goes directly from source → resolve → bound AST → bytecode, skipping any true intermediate representation. This is pragmatically correct (you emit good bytecodes) but means no cross-procedure analysis, no SSA-form optimizations, and no ability to target alternative backends from a common IR.

## VM Execution — 85%

**3,405 lines, 78 instruction handlers, 36 tests, 7 Kani proofs.**

- Register-file architecture with 256-slot initial capacity, dynamically resizable.
- PC-based interpreter with sequential dispatch.
- Full error handling: On Error Resume Next, On Error Goto Label, Err.Number, Resume.
- Call stack management with return address tracking.
- WithEvents binding state (`HashMap<i64, i32>`) and owner iteration.
- Financial function implementations (FV, PV, PMT, NPV, IRR, MIRR, Rate, NPer) with Newton-Raphson solver for Rate.

**Kani formal proofs cover critical invariants:**
- PC progression safety for jump targets.
- Comparator ops produce boolean {0,1} values.
- Financial domain validation (Rate zero-NPer, NPer invalid domain).
- VarType output domain.
- CVErr tag encoding stays in reserved band.
- Resume Next clears Err.Number after Raise.

**Concerns:**
- Single 3,400-line file (`interpreter.rs`) — high complexity concentrated in one module.
- Three entry points (`execute`, `execute_with_typed_fastpaths`, `invoke_procedure_with_i32_args`) with inconsistent reset sequences (per item 9 in the general review).
- Hardcoded `HalProfileId::Windows` in `default_host_services()` (per item 4).

**Assessment:** The VM is functionally complete for the v620 target. Instruction coverage is comprehensive, error handling is robust, and formal verification adds meaningful safety guarantees. The code quality concern is purely structural (monolithic file, inconsistent reset).

## JIT Compilation — 30%

**688 lines total (lib.rs 49 lines, cranelift.rs ~506 lines), 10 tests.**

- Cranelift-based code generation for a 23-instruction subset (29.5% of VM's 78 instructions).
- Supported: arithmetic, comparisons, boolean logic, jumps, ClearErr, IncSlot, Halt.
- Not supported: all string ops, date/time, arrays, COM/events, financial functions, error state transitions, recursive calls.
- **All-or-nothing fallback**: if any instruction in the bytecode is unsupported, the entire program falls back to the VM interpreter. No partial JIT.

**Assessment:** The JIT is experimental. The fallback strategy is correct (output parity is verified by 10 tests comparing JIT vs VM results), but the narrow instruction coverage means virtually all real VBA programs fall back to the VM. This is adequate for the current milestone — JIT performance is a lower priority than correctness per CHARTER.md value ordering (Robustness > Compatibility > Performance).

**Assessment:** COM interop is functionally complete for the v620 parity target. The implementation is correct and well-evidenced. ## Runtime Primitives — 70%

**Gaps:**

**Assessment:** The runtime crate is intentionally thin — the VM operates on i32 register slots and only uses Variant for host bridge marshaling. # Hosting, Project, and Tooling Proposal — Detailed Review

## Overall Assessment

## PR-1. `OxvbaHostBridge` Trait Design — Strong Foundation, Needs Refinement

The proposed trait (section 3.1.2) is well-structured:

```rust
pub trait OxvbaHostBridge {
    fn load_project(&self, id: &str) -> Result<ProjectManifest, HostError>;
    fn load_artifact(&self, id: &str) -> Result<Vec<u8>, HostError>;
    fn resolve_root_object(&self, name: &str) -> Result<HostObjectToken, HostError>;
    fn subscribe_event(&self, object: HostObjectToken, event_name: &str, handler: EventHandlerBinding) -> Result<SubscriptionId, HostError>;
    fn unsubscribe_event(&self, subscription: SubscriptionId) -> Result<(), HostError>;
    fn invoke_method(&self, object: HostObjectToken, method: &str, args: &[Variant]) -> Result<Variant, HostError>;
    fn get_property(&self, object: HostObjectToken, property: &str) -> Result<Variant, HostError>;
    fn set_property(&self, object: HostObjectToken, property: &str, value: Variant) -> Result<(), HostError>;
    fn emit_diagnostic(&self, diagnostic: EngineDiagnostic);
}
```

**Strengths:**
- Uses typed tokens (`HostObjectToken`, `SubscriptionId`) instead of raw `i32` — addresses item 8 from the general review.
- Uses `Variant` for values instead of `i32` tokens — enables real value passing.
- Clean separation: host provides objects/events, engine provides compilation/execution.
- `emit_diagnostic` gives hosts a structured diagnostic sink.

**Suggestions:**

1. **Missing `release_object`** — The same gap identified in the HAL review (H5) exists here. The bridge needs `fn release_object(&self, object: HostObjectToken) -> Result<(), HostError>` for lifecycle management.

2. **Missing `dispatch_event` direction** — The trait defines host→engine subscription (`subscribe_event`), but there is no explicit engine→host event dispatch entry point. The lifecycle sequence (section 3.1.2, step 9) mentions "Host raises events → engine dispatches to WithEvents handlers" but the trait has no method for the host to push an event into the engine. Need either `Engine::dispatch_host_event(subscription: SubscriptionId, args: &[Variant])` on the engine side, or document the mechanism.

3. **`invoke_method` vs `dispatch_invoke` nomenclature** — The HAL uses `dispatch_invoke` (COM-oriented, token-based), while the bridge uses `invoke_method` (string-based, Variant-based). This is correct for their respective layers, but the proposal should explicitly document the mapping between them. When VBA code calls `Application.WorkPanel.Refresh()`, what is the call chain? Engine → bridge `invoke_method("Refresh", &[])` → host implementation. But what about child object navigation? `Application.WorkPanel` requires `get_property("WorkPanel")` returning a `HostObjectToken` — is the returned `Variant` boxing a token? The marshaling contract for object-typed return values needs specification.

4. **Collection/default member access** — The DNA VbCalc object model includes `Controls("name")` (default member access on a collection). The bridge trait has no explicit collection protocol. `invoke_method(controls_token, "Item", &[name_variant])` would work, but the proposal should document whether default member dispatch goes through `invoke_method` with an empty/special method name, or through a dedicated trait method.

5. **Error return semantics** — When `invoke_method` returns `Err(HostError)`, how does this map to VBA's `Err` object? The proposal mentions "Errors route through deterministic error model" but doesn't specify the mapping. Does `HostError` carry an error number that becomes `Err.Number`? Does it carry a source string for `Err.Source`?

## PR-2. DNA VbCalc Pathfinder — Excellent Scope, Right Approach

The pathfinder design (section 3.1.5) is the strongest part of the proposal. The "put us in harm's way" philosophy is exactly right — a minimal stub would miss the hard integration problems.

**Strengths:**
- The object model hierarchy (`Application` → `WorkPanel` → `Controls` → `Control` subtypes) exercises every hosting interaction: root injection, child navigation, collection access, property get/set, method invocation, event subscription.
- The hosting surface coverage checklist (12 aspects) is comprehensive and traceable.
- The `[HOST-REQ]` vs `[APP-IDEA]` distinction is disciplined — it separates engine requirements from application design.
- The `.vbcalc` XML-in-ZIP format exercises the host-managed project store contract.

**Suggestions:**

1. **UI framework decision is missing** — The work panel with interactive controls (text boxes, buttons, labels, list views) requires a UI framework. The proposal doesn't mention one. For a Windows-first pathfinder, options include: Win32 (raw), WinUI 3, WPF (if .NET host), egui (Rust-native, cross-platform), or a web-based UI. This decision affects the implementation timeline significantly. Recommend: decide early and document it. egui would give cross-platform reach; a web-based panel (with a local server + browser) would be simplest to iterate on.

2. **Project reload path** — The checklist includes "Edit VBA, re-compile without restarting host" but the proposal doesn't detail the re-compilation contract. Does the host call `Engine::execute_project_with_snapshot_phased` again with updated source? What happens to live object references, subscription state, and module-level variables? This is one of the hardest problems in VBA hosting (Excel's "reset" behavior is notoriously complex). Recommend: define explicit reset semantics early — at minimum, "full reset" (tear down everything, recompile, restart) as the v1 behavior, with incremental re-compilation as a future goal.

3. **Thread model** — The event pump loop sketch (section 3.1.5) shows a single-threaded polling model. Real hosts often need the VBA engine on one thread and the UI on another (or at least interleaved with UI message pumping). The proposal should state whether the engine is single-threaded-only or if there is a threading contract. Given STA COM requirements on Windows, single-threaded with cooperative yields (via DoEvents) is the pragmatic choice — document it.

## PR-3. Three-Plane Contract (Section 3.1.7) — Critical Architecture

The normative integration split (Host Project semantic plane / HAL service plane / Transport adapter plane) is the most important architectural decision in the proposal. It correctly separates:

1. **What VBA code sees** (host project semantics — types, events, symbols) from
2. **What capabilities are available** (HAL policy — filesystem, COM, UI) from
3. **How values cross the boundary** (transport — COM IDispatch, direct bridge, WASM imports).

**This is the right architecture.** It enables non-COM hosts (DNA VbCalc on Linux, WASM browser sandbox) to provide full host-object semantics without COM dependency, while COM remains a first-class transport adapter on Windows.

**Suggestion:** This three-plane model should be the opening section of the proposal, not buried in 3.1.7. It is the foundational architecture that everything else builds on. Every other use case (UC-B through UC-E) is a variation on how these three planes are configured.

## PR-4. `oxvba.toml` Schema — Well-Designed

The TOML schema (section 4.1.2) is practical and covers the full spectrum:

- `[project]` — name, kind, scope, entry, language version.
- `[layout]` — auto-discover with include/exclude globs.
- `[host]` — default root object, runtime profile, policy preset.
- `[[references.project]]`, `[[references.typelib]]`, `[[references.native]]` — three reference kinds.
- `[build]` — target, flavor, output dir, deterministic mode, prebuild hooks.
- `[extensions]` — top-level code toggle.
- `[conditional_constants]` — compile-time constants.

**Strengths:**
- Schema version with monotonic integer policy — simple and unambiguous.
- Three reference kinds map cleanly to the existing `ReferenceKind` enum.
- Prebuild hooks enable external build integration without hidden magic.
- The auto-discover + include/exclude pattern follows established conventions (Cargo.toml, .csproj).

**Suggestions:**

1. **Missing `[modules]` explicit mapping** — The schema supports auto-discovery, but there is no way to explicitly map a source file to a module kind. If `src/Calculator.cls` should be a Class module but `src/Utils.bas` should be Procedural, the only mechanism is file extension convention. This works for `.bas`/`.cls` but what about Document modules (code-behind) or Form modules? Recommend: add an optional explicit `[[modules]]` table for cases where convention is insufficient:
   ```toml
   [[modules]]
   path = "src/ThisWorkspace.cls"
   kind = "document"
   ```

2. **Missing dependency version constraints** — `[[references.project]]` has `name` and `path` but no version constraint. For add-in distribution (UC-B), version pinning matters. Not critical for v1, but the schema should reserve a `version` field.

3. **Typelib reference `libid` is Windows-specific** — On non-Windows platforms, `libid` (a GUID) and `major`/`minor`/`lcid` are meaningless. The schema should document that typelib references are platform-conditional and will produce deterministic warnings on unsupported platforms.

## PR-11. Risks

1. **Scope creep across 5 use cases** — The proposal covers embedded hosting, add-ins, CLI tooling, top-level code, and WASM. Attempting all five in parallel would fragment effort. The phased plan mitigates this, but discipline is needed to stay on the critical path (P1 → P2 → P4 → P5/P6 → P7).

2. **DNA VbCalc is a full application** — Building a host application with a work panel, control hierarchy, event routing, persistence format, and project reload is a significant undertaking independent of the engine work. The risk is that application-level complexity delays engine contract validation. Mitigation: implement P5a (bridge trait + test harness) first, before committing to the full VbCalc UI.

3. **Variant marshaling layer** — The current engine operates entirely in i32 slot space. The host bridge requires `Variant`-typed arguments. Building the marshaling layer between i32 slots and Variant values is non-trivial (especially for strings, arrays, and object references). This is an implicit dependency of P5 that isn't called out as a separate deliverable.

4. **Event model dependency** — P5 (host contract) and P6 (event closure) are marked as parallel, but in practice the host event bridge (P5) depends on runtime event semantics (P6 EVT3-EVT4). If EVT3 runtime subscription graph semantics change during P6, the P5 bridge may need rework. Mitigation: define the bridge trait with a minimal event contract first, then extend as EVT3-EVT8 stabilize.

This sequence front-loads the highest-value, lowest-risk work (project format and bridge trait) and defers the highest-risk work (full VbCalc application) until the underlying contracts are stable.

## SEC: COM FFI Security Review — standard.rs

All 163 `unsafe` blocks in the codebase reside in `crates/oxvba-hal/src/adapters/standard.rs` (7,385 lines). This section categorises the unsafe surface area, assesses risk, and identifies the single high-priority remediation.

### Unsafe Surface Breakdown

| Category | Count | Representative Lines | Risk |
|----------|------:|----------------------|------|
| COM vtable extern fn dispatchers | 39+ | 3745–3838, 4394–4700 | Medium — FFI boundary, relies on caller contract |
| Raw pointer dereferences (`(*ptr)`) | 95 | throughout | Medium — correctness depends on ref-count discipline |
| Pointer casts (`as *const`/`as *mut`) | 17 | 1533, 2151, 4028, 4178, 4468, 5286 | Low — all between compatible `repr(C)` COM types |
| `Box::into_raw` / `Box::from_raw` pairs | 3 / 3 | 4029/4191, 4056/4918, 4078/5088 | Medium — leak-to-COM / reclaim-on-Release pattern |
| Atomic ref-count ops (fetch_add/sub) | 10 | 4161, 4167, 4890, 4908, 5064, 5085 | Low — AcqRel ordering, saturating_sub guards |
| Vtable function pointer calls | 12+ | 4300, 4574, 5141, 5211, 5263, 5287, 5400+ | Medium — unchecked dispatch across FFI |
| Windows FFI calls (CoInitializeEx, etc.) | 6 | 1025, 1041, 1122, 1132 | Low — standard Win32 COM API |
| Null-pointer initialisations | 29 | `std::ptr::null_mut()` throughout | None — defensive |

### Positive Findings

- **No `transmute`** — the most dangerous unsafe primitive is entirely absent.
- **All casts are between compatible `repr(C)` COM types** — no type-punning across unrelated layouts.
- **Null checks are consistent** at every FFI entry point (lines 1146, 4084, 4097, 4203, 4264, 4279, 4326, 4348, 4461, 4487, 4527, 4543, 4575, 4656).
- **Ref-counting is correct**: `fetch_sub` with `Ordering::AcqRel` followed by `saturating_sub` prevents underflow; `Box::from_raw` runs only when the count reaches zero (lines 4167–4191, 4915–4918, 5085–5088).
- **Memory ordering is appropriate**: `AcqRel` for read-modify-write, `Release` for stores, `Acquire` for loads (lines 4845, 4859, 4868).
- **Cleanup functions are defensive**: `raw_release_dispatch` (5136), `raw_release_connection_point` (5145), `raw_release_unknown` (5156) all guard against null before calling Release.

### Concerns

1. **Self-referential owner pointers** (lines 4022–4029): `OxvbaTestDispatchObject` stores raw pointers to its own sub-interfaces before being leaked via `Box::into_raw`. The invariant is that the object lives on the heap until Release drops it — correct, but entirely undocumented.

2. **Sink lifetime is implicit**: `OxvbaComEventSink` and `OxvbaComEventSourceInterfaceSink` capture `Arc<Mutex<ComState>>` (lines 3269, 3898, 3925, 4035, 4061). The Arc keeps the shared state alive across the FFI boundary, but nothing documents that this is the mechanism preventing use-after-free.

3. **Owner-dereference helpers** (lines 4110–4156): Five `unsafe fn` helpers cast `*mut c_void` back to typed owner pointers by traversing the `owner` field. Each relies on the COM calling convention guarantee that `this` is valid — undocumented.

### Critical Finding: Zero `// SAFETY:` Comments

None of the 163 unsafe blocks carry a `// SAFETY:` comment documenting why the unsafe operation is sound. This is the single highest-priority finding in this review. Rust convention (enforced by `clippy::undocumented_unsafe_blocks`) requires each unsafe block to state its safety invariant.

**Recommendation:** Add `// SAFETY:` annotations to all 163 unsafe blocks. Prioritise the 3 `Box::into_raw`/`Box::from_raw` pairs, the 5 owner-dereference helpers, and the 12 vtable dispatch calls, as these carry the highest correctness risk.
